# LEION HR 招聘自动化与人才档案升级设计规格

- 日期：2026-09-21
- 状态：已批准（用户于 2026-09-21 确认）
- 基线规格：
  - [BOSS 直聘本机全自动筛选 + 共享简历库](./2026-09-16-boss-resume-screening-design.md)
  - [LEION HR 原版设计还原与真实功能融合](./2026-09-21-leion-hr-original-design-restoration.md)

## 1. 目标

在现有 Vue 3 管理台、FastAPI 服务和本机 Playwright Agent 基础上，完成可实际使用的招聘筛选闭环：HR 在 BOSS 直聘人工设置筛选条件并登录后，从管理台启动有限批次任务；Agent 读取当前页面候选人，按岗位要求评分，对达标且资料完整的候选人自动发送固定问候语并索取简历；系统统一保存候选人、岗位关联、简历版本、评估、人工复核、联系与审计记录。

本次升级同时解决现有系统的四个数据断点：候选人无法完整关联多个岗位、简历没有版本链、重复候选人无法安全合并及撤销、缺失资料会被直接硬筛拒绝。

## 2. 成功标准

- 同一候选人只保留一份主体档案，可关联多个岗位；每个岗位拥有独立评估和流程状态。
- 同一候选人的新版简历生成新版本，历史版本和历史评估可追溯。
- 手机号或邮箱匹配时提示人工合并，不自动静默合并；管理员和招聘负责人可以逐字段确认并撤销合并。
- HR 启动任务时选择岗位和 `1–50` 位处理数量；Agent 仅处理当前 BOSS 页面已有筛选结果，不自动修改平台筛选条件。
- AI 根据岗位 JD 提取关键资料及理由，HR 启动前可增删并确认；确认后本次任务锁定该清单。
- 普通资料缺失采用保守默认分并明确标注；总分达标但缺少关键资料时进入人工复核，不自动发送。
- 总分达岗位阈值、关键资料完整且没有历史联系记录时，自动发送岗位固定模板并索取完整简历。
- 验证码、风控提示、登录失效、页面结构异常或 API 不可达时立即暂停，不绕过平台安全机制。
- 评分依据、默认估算项、资料完整度、模型版本、发送结果、失败原因、截图及人工操作均可审计。

## 3. 范围与非目标

### 3.1 本次范围

- 候选人多岗位关联及岗位内状态。
- 简历版本管理、岗位使用版本和手动重新评估。
- 候选人匹配提示、字段级合并和可撤销合并。
- 岗位独立评分阈值、固定消息模板和 AI 关键资料建议。
- 自动筛选任务创建、运行进度、暂停状态和人工复核队列。
- Playwright Agent 按指定岗位和批次数量执行。
- Web 管理台展示和操作上述真实数据。
- 本地演示模式可使用模拟评分结果，但数据结构和流程必须与真实模式一致。

### 3.2 非目标

- 不接入或模拟 BOSS 官方内部接口。
- 不自动设置 BOSS 的岗位、城市、经验等筛选条件。
- 不自动处理验证码，不隐藏自动化特征，不规避风控或访问限制。
- 不做云端无头浏览器、无人值守运行、多账号并发或无限循环任务。
- 不自动做录用或淘汰决定。
- 不在本次加入短信、邮件或其他招聘平台。
- 不因 AI 建议直接淘汰资料缺失的候选人。

## 4. 角色与权限

系统角色扩展为：

- `admin`：管理用户、岗位、任务和全部候选人数据；可合并、撤销合并及人工重新联系。
- `lead`：招聘负责人；可合并、撤销合并及人工重新联系，不能执行管理员专属账号管理。
- `member`：普通 HR；可管理获授权的岗位、启动任务、处理人工复核、上传简历和提交合并建议，不能直接合并或撤销。

现有 `member` 行为保持兼容；数据库迁移后已有 `admin` 权限不变。新增 `lead` 角色必须在 API 权限校验和前端显示中同时生效。

## 5. 总体架构

```text
[Vue 3 管理台]
  岗位 / 任务 / 候选人 / 简历 / 人工复核 / 审计
                    │ JWT
                    ▼
[FastAPI 服务]
  任务状态机 ─ 候选人主体 ─ 岗位关联 ─ 简历版本
       │          │            │           │
       └──────── 评分 / 联系 / 合并审计 ───┘
                    ▲
                    │ HTTPS + 个人 API Key
[本机 Playwright Agent]
  持久化 Profile / 当前页面读取 / 评分编排 / 自动问候
```

核心业务状态全部由 API 保存。Agent 不以进程内变量作为任务事实来源；浏览器或 Agent 重启后可从服务端任务记录判断已处理对象，避免重复发送。

BOSS 页面访问封装在平台适配器中，使候选人库、评分、任务和审计逻辑不依赖具体 DOM。未来获得官方授权接口时可替换适配器，而不重写核心系统。

## 6. 核心数据模型

### 6.1 Candidate

候选人主体保存稳定身份和当前基础资料：

- `id`
- `boss_id`，可空
- `name`
- `phone_normalized`，可空
- `email_normalized`，可空
- `fingerprint`
- `age`，可空
- `years_of_experience`，可空
- `job_segments_json`
- `source`
- `merged_into_candidate_id`，可空
- `created_at`、`updated_at`

手机号和邮箱必须标准化后查询。命中任一字段只生成“疑似重复”提示，不能自动合并。已被合并的候选人保留原记录，但默认查询不再作为独立主体返回。

### 6.2 CandidateJob

独立表达候选人与岗位的多对多关系：

- `candidate_id`
- `job_id`
- `status`：`discovered`、`scored`、`needs_review`、`contacted`、`resume_received`、`archived`
- `active_resume_id`，可空
- `latest_score_event_id`，可空
- `review_reason_json`
- `created_at`、`updated_at`

`candidate_id + job_id` 唯一。同一候选人可以关联多个岗位，各岗位状态、评分和使用的简历版本互不覆盖。

### 6.3 Resume

每次上传或接收的文件都是不可变版本：

- `candidate_id`
- `version_number`：在候选人范围内从 1 递增
- `original_filename`
- `file_path`
- `file_hash`
- `parsed_text`
- `source`
- `parse_status`
- `uploaded_by_user_id`，可空
- `supersedes_resume_id`，可空
- `created_at`

不能覆盖或删除旧文件来表示更新。`CandidateJob.active_resume_id` 表示该岗位当前使用的版本。上传新版后，已有岗位继续使用原版本，直到 HR 手动选择新版并发起重新评估。

### 6.4 ScoreEvent

评分记录不可变，新增：

- `candidate_job_id`
- `resume_id`，可空
- `task_id`，可空
- `score`
- `reason`
- `evidence_json`
- `missing_fields_json`
- `estimated_fields_json`
- `critical_fields_json`
- `confidence`
- `decision`：`below_threshold`、`eligible`、`needs_review`、`error`
- `model`
- `created_at`

历史评分不因重评而覆盖。

### 6.5 ScreeningTask

任务由 HR 在 Web 创建，由指定 Agent 领取：

- `id`
- `job_id`
- `created_by_user_id`
- `machine_id`，可空
- `requested_count`：整数，范围 `1–50`
- `critical_fields_json`
- `critical_fields_source_json`：保存 AI 建议、理由和 HR 修改差异
- `status`：`draft`、`ready`、`running`、`paused`、`completed`、`failed`、`cancelled`
- `pause_reason`
- `processed_count`、`eligible_count`、`contacted_count`、`review_count`、`skipped_count`、`failed_count`
- `created_at`、`started_at`、`finished_at`

任务一经启动，岗位、数量、关键资料清单和模板快照不得修改。若 HR 需要改变规则，应创建新任务。

### 6.6 ScreeningTaskItem

每位候选人在某次任务中的结果：

- `task_id`
- `candidate_id`
- `candidate_job_id`
- `position_index`
- `status`：`discovered`、`scoring`、`needs_review`、`below_threshold`、`contacted`、`duplicate_contact`、`failed`
- `score_event_id`，可空
- `outreach_event_id`，可空
- `failure_code`、`failure_detail`
- `created_at`、`updated_at`

`task_id + candidate_id` 唯一，支持任务恢复时幂等跳过已完成项。

### 6.7 CandidateMerge

合并必须可逆并完整审计：

- `id`
- `source_candidate_id`
- `target_candidate_id`
- `field_choices_json`
- `snapshot_json`
- `performed_by_user_id`
- `performed_at`
- `reverted_by_user_id`，可空
- `reverted_at`，可空
- `status`：`active`、`reverted`

`snapshot_json` 保存合并前候选人字段、岗位关联、简历归属和相关外键映射。撤销必须在事务中按快照恢复；若合并后产生的新记录无法无损拆分，API 拒绝自动撤销并返回明确冲突清单，不允许部分恢复。

### 6.8 OutreachEvent

联系记录用于全局去重，取消现有“候选人 + 岗位唯一即全部规则”的单一表达，增加：

- `candidate_id`
- `job_id`
- `task_id`，可空
- `message_snapshot`
- `status`：`sending`、`sent`、`confirmed`、`failed`
- `failure_reason`
- `manual_override_by_user_id`，可空
- `created_at`、`confirmed_at`

自动任务发送前按候选人全局检查任何成功联系记录，跨任务、跨岗位均不重复发送。只有 `admin` 或 `lead` 能明确创建人工重发授权；授权和原因写入审计。

## 7. 岗位配置与关键资料

每个岗位保存：

- JD 原文。
- `score_threshold`，整数 `0–100`。
- 固定问候模板。
- BOSS 入口配置及既有限速设置。

固定模板仅允许白名单变量：

- `{{candidate_name}}`
- `{{job_name}}`

岗位保存时校验未知变量。任务启动前再次渲染校验；变量缺失或结果为空时禁止发送并将任务项标记为失败。

AI 根据岗位 JD 生成关键资料建议，每项包括稳定键、中文名称和理由。HR 可以增删后确认。确认后的任务快照用于本轮全部候选人，运行中不随岗位 JD 或模型输出变化。

关键资料建议失败时，不允许启动自动发送任务；HR 可手工建立至少一项关键资料并确认后继续。

## 8. 自动筛选流程

### 8.1 登录与任务创建

1. HR 使用专用持久化浏览器 Profile 人工登录 BOSS。
2. HR 在 BOSS 页面人工设置岗位、城市、经验等筛选条件，并停留在结果页。
3. HR 在管理台选择一个启用岗位。
4. 系统根据当前岗位 JD 生成关键资料建议和理由。
5. HR 增删并确认关键资料。
6. HR 输入本次处理人数，范围 `1–50`。
7. 系统创建并锁定任务快照，等待本机 Agent 领取。

系统不得主动改变 BOSS 页面筛选条件。岗位保存的 BOSS 地址只用于打开或校验入口，不能替代 HR 对当前结果页的人工确认。

### 8.2 候选人处理

Agent 按页面顺序处理，最多处理 `requested_count` 位；实际候选人不足时正常完成：

1. 读取当前候选人公开资料。
2. 按 BOSS ID、手机号、邮箱和弱指纹查询主体。
3. 手机号或邮箱命中不同主体时创建疑似重复提示，不自动合并。
4. 建立或获取 `CandidateJob`。
5. 提取评分字段并标记缺失项。
6. 对普通缺失字段使用岗位/评分规则定义的保守默认值，并写入 `estimated_fields_json`。
7. 调用评分服务，返回分数、理由、证据、置信度和模型版本。
8. 若任何已确认关键资料缺失，即使总分达标，也标记 `needs_review`，不发送。
9. 若分数未达岗位阈值，标记 `below_threshold`。
10. 若分数达标且关键资料完整，执行全局联系去重。
11. 未联系过则渲染固定模板、发送并验证消息已出现在会话中。
12. 只有验证成功才写入成功联系记录；仅点击按钮不视为成功。

### 8.3 暂停与失败

以下情况立即暂停整项任务：

- 验证码或风控页面。
- 登录失效。
- 页面结构不符合已知适配器契约。
- API 不可达。
- 当前页面不再是已确认的候选人结果页。
- 候选人身份或当前会话无法在发送前再次确认。

单个候选人的评分服务错误、模板错误或可恢复页面错误只标记该任务项失败；连续三位候选人出现同类页面错误时暂停整项任务。暂停后必须由 HR 检查页面并手动恢复或取消。

### 8.4 联系去重

- 自动发送以候选人主体为全局边界，跨岗位、跨任务默认不重复。
- 合并候选人时，两边联系记录一并归集；存在任何成功联系记录即视为已联系。
- `sending` 状态超过超时阈值时进入人工核验，不能自动重发。
- `admin` 或 `lead` 可填写原因并人工授权一次重发；授权仅对指定候选人和岗位生效一次。

## 9. 人工复核

人工复核列表按岗位展示：

- 候选人。
- 总分、阈值和置信度。
- 缺失的关键资料。
- 使用保守默认分的普通缺失项。
- 评分依据和模型版本。
- 来源任务和处理时间。

HR 可以：

- 补充或修正资料。
- 关联已有简历版本。
- 上传新版简历。
- 选择岗位并手动重新评估。
- 保持待复核或归档。

人工复核不会自动恢复原任务发送。补齐资料后必须产生新的评分事件；只有新结果满足条件时，HR 才能明确执行联系操作或创建新自动任务。

## 10. 候选人合并与撤销

### 10.1 匹配提示

手机号或邮箱任一标准化值相同即提示疑似重复。提示展示双方基础信息、简历版本、岗位关联和联系历史。系统不得因姓名相同自动提示为强匹配，但可以将姓名和弱指纹作为辅助信息。

### 10.2 字段级合并

`admin` 或 `lead` 逐项选择目标值：姓名、电话、邮箱、年龄、经验和来源字段。合并时：

- 所有简历版本保留并重新编号，原版本关系写入快照。
- 岗位关联去重；同岗位冲突时保留双方历史评分，当前状态按更靠后的流程阶段选取并记录选择。
- 联系、交换、任务和审计记录全部保留。
- 来源候选人标记 `merged_into_candidate_id`，不物理删除。

### 10.3 撤销

撤销由 `admin` 或 `lead` 发起：

- 无冲突时事务性恢复全部主体字段、简历归属、岗位关联和外键。
- 合并后新增且无法明确归属的简历、岗位关联或联系记录会形成冲突清单。
- 有冲突时拒绝自动撤销，保持当前数据不变，由有权限人员先明确每条新增记录的归属，再重新执行。
- 每次撤销尝试和结果都写入审计。

## 11. 简历版本与重新评估

- 上传简历必须指定候选人；从 BOSS 收到附件时自动关联当前候选人。
- 同一文件哈希重复上传时返回已有版本，不创建重复版本。
- 新文件创建下一个版本号，并保留原文件和解析结果。
- 新版上传后，系统提示该候选人已有的岗位关联，但不自动切换 `active_resume_id`，也不自动重评。
- HR 选择一个或多个岗位使用新版并手动发起重评；每个岗位独立产生新评分事件。
- 历史评估始终指向当时使用的简历版本。

## 12. Web 管理台

沿用现有 LEION HR 视觉体系，不引入演示数据冒充真实结果。

### 12.1 工作台

- 显示当前任务、处理进度、达标、已发送、待复核、跳过和失败数量。
- 提供创建任务、暂停、恢复和取消入口；按钮只在 API 状态允许时可用。
- 展示 Agent 在线状态和最后错误。

### 12.2 岗位管理

- 编辑 JD、岗位评分阈值和固定问候模板。
- 显示 AI 关键资料建议入口，但关键资料最终按任务确认并锁定。
- 不提供岗位独立招呼额度。

### 12.3 候选人

- 按岗位、流程状态、分数和待复核筛选。
- 详情展示岗位关联、评分证据、风险、联系和活动时间线。
- 提供疑似重复、合并建议、字段级合并及撤销入口，并按角色控制权限。

### 12.4 简历库

- 保持“先选岗位，再看简历”的主交互。
- 展示候选人当前用于该岗位的版本及完整版本时间线。
- 支持上传新版、切换岗位使用版本和手动重新评估。

### 12.5 系统设置

- 展示 Agent、BOSS 登录状态、自动暂停规则和个人 Agent Key。
- 管理员继续管理 HR 账号，并可设置 `lead` 角色。

## 13. API 边界

新增或扩展以下资源：

- `/api/jobs`：岗位阈值和模板。
- `/api/jobs/{id}/critical-fields/suggest`：生成关键资料建议。
- `/api/screening-tasks`：创建、列表和详情。
- `/api/screening-tasks/{id}/start|pause|resume|cancel`：受状态机约束的动作。
- `/api/screening-tasks/{id}/claim`：Agent 领取指定任务。
- `/api/screening-tasks/{id}/items`：Agent 幂等上报任务项。
- `/api/candidates`：岗位和状态过滤。
- `/api/candidates/{id}/jobs`：岗位关联和使用的简历版本。
- `/api/candidates/duplicates`：疑似重复列表。
- `/api/candidate-merges`：预览和执行合并。
- `/api/candidate-merges/{id}/revert`：冲突检查后撤销。
- `/api/resumes`：按候选人和岗位查询版本。
- `/api/resumes/upload`：上传时指定候选人。
- `/api/candidates/{id}/jobs/{job_id}/re-evaluate`：选择版本后重评。
- `/api/reviews`：人工复核队列和处理。
- `/api/outreach/{candidate_id}/override`：仅 `admin`/`lead` 创建一次性人工重发授权。

所有写接口必须校验 JWT 或个人 Agent API Key、角色、资源状态和幂等键。

## 14. 数据迁移与兼容

- 迁移必须同时支持 SQLite 开发库和 PostgreSQL 生产库。
- 现有候选人按原 ID 保留。
- 现有 `ScoreEvent` 和 `OutreachEvent` 根据 `candidate_id + job_id` 回填 `CandidateJob`。
- 现有简历按候选人及创建时间回填版本号；无候选人的简历保留为待认领记录，不强行匹配。
- 现有成功联系记录纳入全局去重。
- 迁移不得删除原文件或历史事件。
- 迁移前后记录数量、外键完整性和唯一约束必须由自动测试验证。

## 15. 安全、隐私与合规

- 仅使用招聘人员本人授权的本机登录会话。
- 不保存 BOSS 密码，不复制用户日常 Chrome 配置目录；使用专用持久化 Profile。
- 不绕过验证码、风控、登录限制或平台权限。
- 上线前由企业确认 BOSS 用户协议、招聘者规则及候选人数据处理义务；平台明确不允许时停止自动操作。
- 手机号、邮箱和简历文件按敏感数据管理；生产数据库和备份应加密并限制访问。
- 普通日志不得输出完整手机号、邮箱、简历正文、JWT、API Key 或浏览器会话数据。
- API Key 仅展示一次，数据库只保存哈希。
- 合并、撤销、重发授权、关键资料修改和任务控制写入审计日志。

## 16. 错误处理

- LLM 返回非法结构：有限重试两次，仍失败则任务项 `failed`，不发送。
- 模板变量无效：阻止岗位保存；运行时发现历史坏数据则任务项失败。
- 简历解析失败：保留原文件和版本，标记失败，不伪造解析内容。
- 重复发送不确定：转人工核验，不自动重试。
- Agent 崩溃：任务保留 `running` 心跳超时状态，服务端标记 `paused`；恢复后从未完成项继续。
- 页面候选人不足：按实际人数正常完成。
- 数据合并或撤销冲突：整个事务回滚并返回冲突清单。

## 17. 测试策略

### 17.1 Domain 与 API

- `requested_count` 的 `0/1/50/51` 边界。
- 同一候选人多岗位的状态隔离。
- 手机号或邮箱命中只创建提示，不自动合并。
- 字段级合并保留简历、岗位、评分和联系记录。
- 无冲突撤销成功；存在新增归属冲突时完整回滚。
- 简历版本递增、同哈希幂等和岗位主动切换。
- 普通缺失字段使用保守默认分并进入估算记录。
- 关键资料缺失且分数达标仍进入人工复核。
- 全局联系去重和一次性人工重发授权。
- 任务状态机的非法转换被拒绝。

### 17.2 Agent

- 仅处理当前 fixture 页结果，不操作筛选器。
- 精确处理指定的 `1`、`50` 和少于请求数量的候选人。
- 任务恢复不重复评分或发送已完成项。
- 发送后只有页面验证成功才上报成功。
- 验证码、风控、登录失效和 DOM 异常立即暂停。
- 连续三次同类页面错误触发暂停。

CI 使用本地 HTML fixture，不访问真实 BOSS。真站只通过人工验收清单执行。

### 17.3 Web

- 不同角色的合并、撤销和重发权限。
- 任务人数仅允许 `1–50`。
- 关键资料建议可增删并在任务启动后锁定。
- 人工复核显示缺失项、估算项、置信度和证据。
- 简历版本时间线、岗位使用版本和手动重评。
- 加载、空数据、错误和暂未接入状态不显示虚假数据。

## 18. 验收流程

1. HR 使用专用 Profile 人工登录 BOSS，并在结果页设置筛选条件。
2. 在管理台选择岗位，确认 AI 建议的关键资料，输入 `1–50` 人并启动任务。
3. Agent 不修改筛选器，只按当前结果页顺序处理指定数量。
4. 未达标候选人不联系；关键资料缺失候选人进入人工复核；达标且完整候选人自动发送固定模板。
5. 再次运行相同或其他岗位时，已成功联系的候选人不会自动重复发送。
6. 上传新版简历后，旧岗位评估保持不变；HR 选择岗位和版本后才产生新评分。
7. 创建两个疑似重复候选人，完成字段级合并后所有历史保留；无冲突时可完整撤销。
8. 人工触发验证码或使用 fixture 模拟风控后，任务立即暂停且无后续发送。

## 19. 实施顺序

1. 数据模型、迁移和角色权限。
2. 候选人多岗位及简历版本。
3. 合并、撤销和审计。
4. 关键资料建议、缺失字段语义和人工复核。
5. 任务状态机、任务项和全局联系去重。
6. Agent 指定岗位、`1–50` 批次及暂停恢复。
7. 管理台任务、候选人、简历和复核界面。
8. 全量回归、构建和真站人工验收。

## 20. 已确认决策摘要

- 一份候选人主体可关联多个岗位。
- 新版简历保留历史版本，已有岗位由 HR 手动选择是否重评。
- 手机号或邮箱命中时提示人工合并。
- 合并采用字段级人工确认并支持撤销。
- 管理员和招聘负责人可以合并及撤销。
- BOSS 达标候选人通过站内消息自动问候并索要简历。
- 使用 Playwright 本机桌面执行器，人工登录后运行。
- 每个岗位独立设置评分阈值，使用固定消息模板。
- 同一候选人默认跨任务、跨岗位不重复发送。
- 首版达标后直接发送，但必须满足资料完整、去重和发送结果校验。
- HR 每次自行选择处理人数，硬范围为 `1–50`。
- 普通资料缺失使用保守默认分并明确标注。
- 总分达标但关键资料缺失时进入人工复核。
- AI 根据 JD 建议关键资料，HR 可修改并在任务启动前确认。
- Agent 仅处理 HR 当前 BOSS 页面已有筛选结果，不自动设置筛选条件。
