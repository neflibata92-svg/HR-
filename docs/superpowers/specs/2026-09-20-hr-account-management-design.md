# HR 账号管理与首次改密设计

- 日期：2026-09-20
- 状态：已批准（用户确认）
- 基线规格：[云端部署 + 登录鉴权](./2026-09-16-cloud-auth-design.md)
- 关联原型：[LEION HR 可点击管理后台原型](./2026-09-20-leion-hr-clickable-prototype-design.md)

## 1. 目标

为 LEION HR 增加由 HR 总负责人统一管理普通 HR 账号的能力，并同步完善可点击原型与真实系统。

成功标准：

- `admin` 在界面中显示为“HR 总负责人”，可查看、创建、停用和重新启用普通 HR 账号。
- `member` 在界面中显示为“HR”，不能查看或调用账号管理能力。
- 管理员创建账号时设置临时密码，新 HR 首次登录必须修改密码后才能使用业务功能。
- 界面中的“删除”采用软停用，不物理删除用户及历史数据。
- 停用后，该用户的 JWT 与 API Key 均不能继续访问系统。

## 2. 已确认决策

| 项目 | 决策 |
|---|---|
| 角色模型 | 沿用 `admin/member`，不新增角色体系 |
| 界面名称 | `admin` 为“HR 总负责人”，`member` 为“HR” |
| 创建权限 | `admin` 只能创建 `member`，不能通过界面或该接口新增管理员 |
| 登录账号 | 自定义用户名 |
| 初始密码 | 管理员人工设置临时密码 |
| 首次登录 | HR 必须先修改临时密码，之后才能进入业务页面 |
| 删除规则 | 软停用，保留用户和历史数据，可重新启用 |
| 管理员保护 | 账号管理功能不允许停用或修改任何 `admin` |
| 多 HR 调用架构 | 共用一套后端 API，每位 HR 使用独立账号与凭证，第三方 API Key 仅由后端集中保管 |

## 3. 范围与非目标

### 3.1 本期范围

- 更新静态可点击原型中的系统设置页面，增加 HR 账号管理演示。
- 在真实 API 中增加账号列表、创建、停用、启用、首次改密和管理员重置临时密码能力。
- 在真实 Web 管理台中增加管理员账号管理界面和首次改密流程。
- 增加数据库字段迁移、权限保护、错误反馈和自动化测试。

### 3.2 非目标

- 不新增 `hr_manager`、`viewer` 等角色。
- 不引入通用 RBAC 权限表。
- 不物理删除用户。
- 不开放普通 HR 自助注册。
- 不在本期实现邮箱、手机号、短信或邮件通知。
- 不允许管理员在管理界面创建或管理其他管理员。

## 4. 页面与交互设计

### 4.1 静态原型

在“系统设置”中增加仅供演示的“HR 账号管理”区域：

- 展示用户名、账号类型、账号状态、是否需要改密、创建时间。
- 提供“新增 HR”按钮，表单包含用户名、临时密码、确认密码。
- 有效账号提供“停用”操作，停用账号提供“重新启用”操作。
- 停用前显示二次确认。
- 使用演示数据完成新增、停用和启用交互，并明确标注数据不会保存。
- 原型登录页增加“临时密码首次登录后需修改”的演示路径。

### 4.2 真实 Web 管理台

系统管理区域按权限展示：

- `admin` 可见“HR 账号管理”。
- `member` 不显示该入口；即使手工请求接口，后端仍返回 `403`。
- 账号列表展示：用户名、角色显示名、状态、首次改密状态、创建时间、可用操作。
- 新建 HR 时只接受用户名、临时密码和确认密码，角色固定为 `member`。
- 停用和启用成功后刷新对应行；失败时保持原页面状态并显示后端错误。
- 管理员可为普通 HR 重置临时密码。重置后，该用户再次登录时必须修改密码。

### 4.3 首次改密页

用户使用临时密码登录后：

- 只进入“修改初始密码”页面，不展示业务导航和业务数据。
- 输入当前临时密码、新密码和确认密码。
- 修改成功后，后端签发新的访问令牌和刷新令牌，前端替换旧令牌并进入工作台。
- 修改失败时保留页面并显示明确原因。

## 5. 数据模型

在 `users` 表增加：

```text
must_change_password: boolean, not null, default false
```

规则：

- 现有账号迁移后默认 `false`，避免影响已有管理员和 HR。
- 管理员新建或重置普通 HR 密码时设为 `true`。
- 用户成功修改密码后设为 `false`。
- `role` 继续限定为 `admin/member`；账号管理请求不接受客户端传入角色。

本期不新增物理删除标记，继续使用现有 `is_active` 表示有效或停用。

## 6. API 设计

### 6.1 当前用户信息

`GET /auth/me`

返回现有字段，并增加：

```json
{
  "must_change_password": true
}
```

Web 据此决定进入首次改密页还是业务页面。

### 6.2 管理员查看账号

`GET /auth/users`

- 权限：仅 `admin`。
- 返回全部用户，供界面展示。
- 管理界面只对 `member` 提供可操作按钮。

### 6.3 管理员创建 HR

`POST /auth/users`

请求：

```json
{
  "username": "zhangsan",
  "temporary_password": "临时密码"
}
```

规则：

- 后端固定创建 `role=member`、`is_active=true`、`must_change_password=true`。
- 请求体不再允许选择 `admin` 或传入任意角色。
- 用户名重复或密码不符合要求时返回 `400`。

### 6.4 停用与启用

`PATCH /auth/users/{user_id}/status`

请求：

```json
{
  "is_active": false
}
```

规则：

- 仅 `admin` 可调用。
- 目标必须是 `member`；任何 `admin` 都不可通过此功能停用或启用。
- 不物理删除数据。
- 停用后所有后续 JWT、Refresh Token 和 API Key 校验均因 `is_active=false` 失败。

### 6.5 管理员重置临时密码

`POST /auth/users/{user_id}/reset-password`

请求：

```json
{
  "temporary_password": "新的临时密码"
}
```

规则：

- 仅 `admin` 可调用，目标必须是 `member`。
- 更新密码哈希并设置 `must_change_password=true`。
- 目标用户下次登录必须完成首次改密。

### 6.6 用户修改密码

`POST /auth/change-password`

请求：

```json
{
  "current_password": "当前密码",
  "new_password": "新密码"
}
```

规则：

- 需要有效 JWT，不接受 API Key。
- 必须验证当前密码。
- 新密码符合密码策略且不能与当前密码相同。
- 成功后设置 `must_change_password=false` 并签发新令牌。

## 7. 鉴权与数据流

### 7.1 登录与首次改密限制

1. 用户提交用户名和密码。
2. 后端验证账号存在、密码正确且 `is_active=true`。
3. 后端签发令牌，`GET /auth/me` 返回 `must_change_password`。
4. 若为 `true`，Web 只展示首次改密页。
5. 后端同时在业务鉴权层阻止该用户访问除 `/auth/me`、`/auth/change-password` 和退出相关流程之外的业务接口，不能只依靠前端隐藏。
6. 改密成功后签发新令牌，用户进入工作台。

### 7.2 停用即时生效

现有鉴权会在每次 JWT 或 API Key 请求时查询用户并检查 `is_active`。停用提交成功后：

- 已签发 JWT 的后续请求返回 `401`。
- Refresh Token 不能换发新令牌。
- 用户所属 API Key 的后续请求返回 `401`。
- 历史岗位、候选人、简历及审计记录保持不变。

### 7.3 角色边界

- 普通 HR 调用账号管理接口统一返回 `403`。
- 创建、状态切换和密码重置接口均在后端固定目标角色为 `member`。
- 不依赖前端传入角色或前端隐藏按钮保证安全。

### 7.4 多 HR 与第三方服务调用

系统采用“一套后端 API、多位 HR 独立身份”的方式：

- 所有 HR 共用同一个后端 API 地址，但每位 HR 必须使用自己的 JWT 或个人 Agent API Key。
- 系统 API Key 绑定具体 `user_id`，用于识别调用者、独立停用和后续审计；不同 HR 不共用同一系统 API Key。
- 大模型等第三方服务的 API Key 只保存在 API 服务端环境或 Secret 管理系统中，不返回给 Web，也不下发到本机 Agent。
- 本机 Agent 使用个人系统 API Key 请求后端评分接口，由后端代为调用第三方服务。
- 某位 HR 被停用或其个人系统 API Key 被吊销后，不影响其他 HR 使用统一后端。
- 后续可按 `user_id` 增加调用次数、成本和限流统计，本期先确保身份可追踪和密钥不外泄。

需要明确区分两类密钥：

- **系统 API Key**：由本系统签发给某位 HR 的本机 Agent，用于访问统一后端。
- **第三方 API Key**：由大模型等外部供应商签发，只允许后端服务持有。

当前 Agent 直连第三方大模型的实现需要迁移到后端；迁移完成后，Agent 配置中不得再包含第三方 `LLM_API_KEY`，后端缺少该密钥时应明确返回服务不可用，不能使用固定占位分数代替真实评分。

## 8. 密码与错误规则

密码沿用项目现有哈希实现，并统一新增账号、重置密码和修改密码的校验规则。最低要求在实现阶段复用现有配置；若项目目前无统一策略，则采用：

- 至少 8 个字符。
- 新密码不能与当前密码相同。
- 密码和确认密码一致性由前端先校验，后端仍独立校验实际密码字段。

主要错误反馈：

- 用户名重复：`该用户名已存在`。
- 密码不合规：返回具体要求。
- 当前密码错误：`当前密码不正确`。
- 普通 HR 越权：`403`。
- 用户不存在：`404`。
- 对管理员执行停用、启用或重置：`403`。
- 状态与请求一致时采用幂等成功，返回当前用户状态。
- 网络失败时前端不乐观修改状态，保留原数据并允许重试。

## 9. 代码边界

预计改动范围：

- 静态原型 HTML 与原型测试。
- SQLAlchemy `User` 模型和数据库迁移。
- 认证请求/响应 schema、认证 service、认证路由及鉴权依赖。
- Web API 客户端、登录状态控制、首次改密页和管理员账号管理组件。
- 后端鉴权与前端交互测试。

正式 Web 当前集中在单个 `App.vue` 中；本功能应拆出独立账号管理和首次改密组件，避免继续扩大根组件。暂不为本功能引入复杂权限框架。

## 10. 测试与验收

### 10.1 API 测试

- `admin` 可列出用户并创建角色固定为 `member` 的 HR。
- `member` 调用列表、创建、状态切换和重置密码接口返回 `403`。
- 客户端无法通过创建接口注入 `admin` 角色。
- 重复用户名和弱密码返回明确错误。
- 新 HR 登录后 `must_change_password=true`。
- 未完成首次改密的 HR 不能访问业务接口。
- 正确当前密码可完成改密；错误当前密码失败。
- 改密后 `must_change_password=false`，新令牌可访问业务接口。
- `admin` 可停用和重新启用 `member`。
- 停用后已有 JWT、Refresh Token 和 API Key 均无法继续使用。
- 账号管理功能不能操作任何 `admin`。
- 状态重复提交保持幂等。

### 10.2 Web 测试

- 普通 HR 不显示账号管理入口。
- 管理员可查看、创建、停用、启用和重置普通 HR。
- 新增与重置表单校验密码确认。
- 停用操作具有二次确认。
- 临时密码登录后只能看到首次改密页。
- 操作失败时列表状态不被错误改变。

### 10.3 原型验收

- 系统设置中能完整演示新增、停用和启用 HR。
- 普通 HR 与 HR 总负责人视图差异清晰。
- 临时密码首次登录到修改密码的路径可点击演示。
- 原型明确提示演示数据不会保存。

## 11. 实施顺序

1. 完善静态原型并完成产品验收。
2. 增加数据字段和后端账号管理接口。
3. 增加首次改密后端限制与令牌流程。
4. 实现 Web 管理界面和首次改密页面。
5. 完成自动化测试与整体回归。

## 12. 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 只在前端限制首次改密 | 后端业务鉴权同步拒绝受限用户 |
| 停用后旧令牌继续有效 | 每次 JWT、Refresh Token 和 API Key 校验用户有效状态 |
| 管理员误操作管理员 | 所有管理接口只允许目标角色为 `member` |
| 临时密码泄露 | 首次登录强制改密；管理员可再次重置；生产环境使用 HTTPS |
| 用户历史数据丢失 | 仅软停用，不删除用户和关联记录 |
| 根组件继续膨胀 | 账号管理和首次改密拆为独立组件 |
